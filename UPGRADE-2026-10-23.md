ESP-Matter 1.6.1 is the latest stable registry release checked for this work. Its [release documentation](https://github.com/espressif/esp-matter/blob/release/v1.6.1/README.md) identifies Matter 1.6.1 support and recommends IDF 6.0.2. The manifest pins this pairing; native, Docker, CMake presets and CI agree. IDF 6.1 was not substituted for the vendor-recommended pairing.

Thread continues to advertise **1.4.0** with an updated host implementation. The [Thread Group offers a 1.4.1 specification](https://threadgroup.org/ThreadSpec), but [IDF 6.0.2 selects `OT_THREAD_VERSION_1_4`](https://github.com/espressif/esp-idf/blob/v6.0.2/components/openthread/private_include/openthread-core-esp32x-ftd-config.h). This is not a verified Thread 1.4.1 implementation upgrade.

The H2 remains on stock RCP firmware `openthread-esp32/50c71d69b84-a12ff0d0f; esp32h2; 2026-04-10 09:57:39 UTC`. The S3 runs the full Thread stack and H2 provides radio/MAC through Spinel; see the [RCP architecture](https://openthread.io/platforms/co-processor) and [board documentation](https://docs.m5stack.com/en/core/CoreS3_Thread_BR). No verified board-specific replacement/recovery image was available, so automatic RCP updating remains disabled. Successful host/RCP startup and attachment were checked on the device.

Video 2.0.1, camera sensor 2.0.1 and codec 1.5.11 stay within the BSP's supported dependency ranges. Forcing newer incompatible parent ranges would require a separate camera/BSP port. The removed private sensor accessor prepares that future migration without claiming it has been completed.

## Application fixes

- Migrated ePSKc crypto to IDF 6's Mbed TLS 4.1 / PSA initialization and secure randomness, while retaining EC-JPAKE and AES-128-CCM-8. The transport supports both Mbed TLS API families in host tests.
- Made UDP nonblocking and bounded the complete ePSKc exchange and response waits. Numeric addresses avoid an unbounded DNS lookup; retry/ACK traffic cannot continually extend the deadline. Fault tests cover silent peers, retry handling and cleanup.
- Serialized the boot camera probe with the UI camera worker. Removed private `esp_video` access and raw sensor register writes; mirrored QR codes use quirc's supported flip/decode fallback. The preview now uses native sensor orientation and may appear mirrored.
- Corrected compile-time Wi-Fi credential bounds to allow a full 32-byte SSID and a 64-character hexadecimal PSK; invalid defaults are ignored. The runtime credential path already supported those bounds. Migrated renamed Wi-Fi reason constants without changing their wire values.
- Coalesced only the exact duplicate-MLE warning in retained logs, including the different IDF 5 and IDF 6 formats. The full `duplicate_mle_count` remains available in `/logs` and survives supported warm resets. Security errors and warnings with extra peer detail remain intact; console output is unchanged.
- Kept Matter identity names bound to the application provider before the new Basic Information implementation captures its provider reference. Vendor/product IDs and fallback manufacturing metadata continue to come from the SDK provider.
- Removed the stale reboot label after applying the device name.

IDF 6 migration also declares individual GPIO/UART/I2C/temperature driver dependencies, regenerates configuration from defaults, and preserves Thread RX-on-when-idle, DVP task stack size, the dedicated Matter NVS labels and the PSRAM no-init log region. The native wrapper selects SDK 6 locally and restores the caller's process environment.

## ESP-Matter 1.6.1 build workaround

The legacy dispatcher retains lighting callbacks even with those clusters disabled. In this configuration its generated sources reference Scenes helpers that the managed build omits. A narrowly version/configuration-guarded block in `CMakeLists.txt` compiles the same six provider/core helper sources used by the vendor's Scene-enabled build. Scenes remains disabled, and no Scenes endpoint is created. Managed components and installed SDK sources are not modified. Remove this block when an upstream release fixes the dispatcher selection.

## Flash and preservation

A full 16 MiB recovery dump was read and verified before the first write. It is stored privately outside the repository because it contains credentials. Its application validation hash and embedded ELF identity matched the old running firmware.

The CoreS3 identity was checked on COM5 before writing. The partition table is byte-for-byte unchanged. Sparse writes update the bootloader, table and application only. With the device held in the loader, both the legacy NVS and `matter_nvs` were read immediately before and after writing and compared byte-for-byte before allowing the new firmware to boot. Both comparisons passed.

The decoded active Thread dataset digest remains `82cc9025cf252d5dd84a1abb364959a946b48875183f05ccaee701a7c0f67105`. No live dataset, TAP, Wi-Fi password, Matter onboarding code or private recovery dump is reproduced in this report. Recovered device provisioning was not copied into the firmware images. Firmware retains the SDK development commissioning credentials described in README.

`firmware/cores3-epskc-commissioner.bin` is a **fresh-install image** and spans the NVS area. Do not use it to update an already provisioned device. Use the sparse `flash_args`/native `-Full` workflow for the first SDK 6 update; later compatible updates can use app-only flashing.

## Validation

- Native ESP32-S3 target build completed successfully. The final application occupies 2,882,240 bytes of its 7 MiB app partition, with 61% free. The map places the no-init log ring in PSRAM at `0x3c2c69c0..0x3c326a80`.
- The final full host suite passed: 12 entrypoints (nine Python scripts and three standalone C programs), including 15 Python unittest cases plus C scenarios/assertions. Coverage includes Wi-Fi transactions and credential/port boundaries; settings/PMIC/power/history; battery recorder; Matter battery worker/conversion and identity-provider timing/metadata; UI wake; production log ring and log tail; camera ownership; REST wire/codec parsing; ePSKc production transport against both Mbed TLS API variants.
- Actual quirc library decoded upright and horizontally mirrored vendor PGM fixtures to identical payloads.
- Layout geometry check found zero problems across 18 panels plus the header. The user confirmed the upgraded screen and touch controls work normally.
- Two consecutive final-device camera self-tests each captured 40 frames at 320×240 and reported `camera OK`, exercising capture shutdown/reopening. No QR was presented to the camera.
- Live DTLS self-fetch negotiated `TLS-ECJPAKE-WITH-AES-128-CCM-8`, accepted the commissioner petition and retrieved the unchanged dataset. Same-dataset application briefly reattaches Thread; the console's 20-second attachment window can expire before attachment completes, so the verifier checks subsequent attachment separately.
- The final live self-fetch completed in 10.412 seconds, observed the ephemeral key's started/connected/accepted states, reattached as a child, preserved the dataset and explicitly stopped the key afterward.
- A live silent UDP peer received four datagrams; DTLS failed with timeout `-0x6800` in 16.041 seconds. A subsequent worker operation completed in 0.126 seconds, with dataset, Matter commissioning state and uptime preserved.
- Home Assistant re-interviewed the existing Matter node and read the upgraded software version and correct M5Stack/CoreS3/K149 identity over the preserved Home fabric. Battery voltage reports continued. No recommissioning was needed.
- MeshCoP mDNS discovery advertised Thread 1.4.0, the original network and a working border-agent port. Radio TX/RX counters advanced with the stock H2.
- Live log coalescing retained one example from 13 duplicate warnings, then two examples from 21 across the next interval; the complete counter remained visible. No panic, task watchdog, stack overflow or corrupt-heap marker appeared in the captured current-boot logs.
- Three forced application-level Wi-Fi disconnects recovered automatically, with the same firmware/uptime, preserved commissioning and Thread attachment. Expected send failures were logged during the induced link outage.

The final image was flashed and its complete ELF digest matched the console both before and after an authorized software reboot. Boot count advanced from 1 to 2, the boot ID changed, and `/logs?boot=previous` matched the prior boot ID with its final sequence and full duplicate counter (23) preserved. The active dataset digest remained unchanged, the ephemeral key was stopped and Thread reattached as a child. Home Assistant reported the same Home fabric and correct identity, with a fresh 4.120 V battery update after reboot. Wi-Fi returned without manual credentials. Post-reboot sampling showed about 53 KB internal heap free (largest block 21 KiB), 6.96 MB PSRAM free and no captured panic/watchdog/heap-corruption marker.

Startup and deliberate link changes produced transient netif/mDNS/report-send warnings. Subsequent MeshCoP discovery, Thread attachment and Matter communication were verified; this report does not treat those warning lines as proof of an ongoing outage.

Docker's engine was unavailable, so Docker and remote CI were not executed. The complete native target build was executed. Physical QR scanning, a different vendor's ePSKc peer, key replay rejection, long-duration battery discharge, and end-to-end routed traffic through another Thread device were not tested. Device capture and synthetic mirrored QR decoding cover different parts of the camera path.
