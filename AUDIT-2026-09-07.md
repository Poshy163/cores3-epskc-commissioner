# CoreS3 audit — 7 September 2026

The application audit produced focused reliability and input-validation fixes,
passing host regressions and a native ESP-IDF build. After the user approved backup, app-only flashing and reversible hardware tests,
the S3 was backed up and updated. Wi-Fi, Thread and Matter provisioning survived.
The H2 firmware, partition layout and dependencies were not changed. No commit,
push or release was made. The baseline below records the original firmware;
the deployment section records subsequent hardware results.

## Baseline and coverage

  changes remain uncommitted. No repository `AGENTS.md` was found.
- Hardware: COM5 enumerates as Espressif USB Serial/JTAG (`303A:1001`); COM4 is
  another vendor's camera. The project targets the M5Stack CoreS3 Thread BR/K149,

  09:57:39 UTC`. H2 firmware was not read, erased, built or flashed.

  IDF Python environment `idf5.5_py3.14_env`. The build uses the documented

  LVGL 9.5.0, LVGL port 2.9.0, esp_video 2.0.1, quirc 1.2.0.

the redacted copies. No key/dataset/onboarding-code endpoint or `reveal` command
was invoked. Captures use inactive DTR/RTS, preserve uptime, and carry UTC markers.

60 seconds passive listening) with `link`, `thread`, `power`, `settings`,
`matter status`, and `status`. The board was powered over USB on its existing

Thread was attached as a router for 20,603 seconds, with 16 routers known locally,
no directly attached children and no parent moves. These counts are not a complete
network census. Matter remained commissioned at endpoint 1 (`0x0091`), window
closed. USB was 4.907 V, battery 100% at 4.118 V, PMIC 38 C, ESP32 41 C.

Twelve `Mle: Failed to process UDP: Duplicated` warnings occurred between device
uptimes 20,627,378 and 20,695,268 ms. There was no captured panic, allocation
failure, watchdog reset or Wi-Fi disconnection. The pinned `mle.cpp` checks at
the frame-counter/key-sequence validation explain **where replay rejection
occurs**, not which peer or network condition caused these packets. That cause
needs packet/peer evidence. The checks and warnings remain intact.

Live REST returned HTTP 200 for `/node/state` (`router`), `/node/ba-epskc/state`
(`enabled`) and `/node` (`State=router`). Observed individual request times were

A 12-second mDNS browse found this device's normal `_meshcop._udp` advertisement
with Thread version 1.4.0 and the expected TXT key set. No `_meshcop-e` service
was seen; a share window was not opened for the audit.

## Implemented findings, ordered by impact

All defects below are confirmed from production code. Only the failures named
as host-reproduced were deliberately exercised; none was injected into the live
network.

| Impact | Root cause and fix | Validation |
|---|---|---|
| High: provisioning loss | `main.c::app_wifi_join` continued after RAM-storage selection failed, allowing an untested candidate to be saved. It now aborts before disconnect/write. Failed FLASH selection/save returns failure instead of claiming saved success. | Original function fails the new host assertion; fixed transaction passes failure/success/rollback cases |
| High: silent deprovisioning | Boot erased main/Matter NVS on no-free-pages or incompatible-version errors. Both paths now preserve data and emit an explicit recovery diagnostic. Main boot still fails; Matter startup fails without deleting fabrics. | Source/pinned storage contract review and native build; no flash-corruption injection |
| High: malformed CoAP | `meshcop.c` read truncated extended-option bytes without bounds checks and incorrectly handled extended lengths. `meshcop_codec.h` validates version, tokens, option encoding/bounds, ACK form and success class. | Production codec tests for short/reserved/extended encodings and a valid 269-byte option |
| Medium: false commissioning progress | A CoAP response alone was called petition acceptance. The fetch now requires MeshCoP State Accept and rejects error-class dataset replies. Console join validates port bounds and returns failure when dataset application/attachment is unconfirmed. | Actual Accept/Reject/missing/truncated State tests and port boundaries; live exchange pending |
| Medium: scan memory/error handling | `app_wifi_scan` leaked driver-owned results when counting/allocation failed and ignored retrieval errors. It now checks errors and frees unconsumed results. | Fault-injected scan/count/allocation/retrieval failures, duplicate filtering and capacity tests |
| Medium: unsafe retry after failed rollback | Watchdog treated the current driver config as persisted NVS and could clear a hold on the rejected RAM candidate. Holds now require explicit join/leave/reboot to release. Diagnostics label driver state accurately. | Transaction rollback tests and source review; timed live failure injection pending |
| Medium: HTTP ambiguity/invalid JSON | Embedded NULs and malformed quoted values could be accepted; names were interpolated unescaped. Production wire helpers reject ambiguous bodies and invalid JSON integer grammar and escape names correctly. | Direct helper tests with body bounds/NUL, quotes/control characters, malformed fields and overflow |
| Medium: stale service/Matter state | Renaming left an active `_meshcop-e` record under the old name; Matter delegate name storage was updated outside the CHIP lock. Active service is withdrawn/re-added and delegate writes are serialized. | Pinned API/source review and native build; active-share rename test pending |
| Medium: QR cancellation race | Retry cleared the abort flag before discovering the previous scan was still busy. Retry now checks ownership first; cancellation flag access is protected. `qrscan_poll` rejects null/zero-capacity destinations before frame dequeue. | Source/concurrency review and native build; repeated cancel/retry on camera pending |
| Lower: misleading telemetry/settings | A failed PMIC Status2 read looked like valid trickle charge. It now returns an error; pointer inputs are checked. Settings validate boolean bytes and report set/commit errors. | Actual PMIC and NVS-stub tests; hardware faults not injected |
| Maintenance | `status` includes IDF version and ELF SHA-256; version dirtiness includes staged edits; CLion docs now correctly explain fullclean/config and serial-reset behavior; host regressions run in CI. | Build/image inspection, host tests and documentation review |

The API remains intentionally unauthenticated for OTBR compatibility. Dataset
access still exposes Thread credentials to clients with network access, as
documented before this audit. No endpoints, authentication contract, partition
layout, dependency versions, watchdog limits, radio policy or H2 firmware changed.
Valid existing REST requests remain supported; malformed requests now fail.

## Checks and limits

- Clean-source native baseline: passed; confirmation build with tracked diff
  empty passed. Baseline image `0x29fb20` bytes; app partition `0x700000`, 63% free.
- `python tools/run_host_tests.py --cc <host compiler>`: passed. Uses real
  production C helpers/functions with mocked external drivers, not a second
  implementation. Wi-Fi has 18 scenarios plus port boundaries; REST/CoAP,
  settings and PMIC tests cover the cases above. Hardware scheduling is not
  simulated by these tests.
- `python -B tools/layout_check.py build/audit-after/layout.svg`: passed, zero
  problems across 17 panels and header; 10 modeled truncations and 14 intentional
  compact-target exemptions. It does not prove actual rendering or touch behavior.
- First reviewed native build: passed. Its image is **2,753,824 bytes** (`0x2a0520`),
  **2,560 bytes larger** than baseline, with **4,586,208 bytes / 62.48%** of the
  application partition free. Bootloader configuration and partition layout are unchanged.
  `esptool image_info --version 2` verifies the image checksum/hash, ESP32-S3,
  `888f04a*`, IDF 5.5.4, and a matching ELF hash. Frozen local evidence is in
  `build/audit-after/artifacts.json` and `image-info.txt`.
  App SHA-256: `33d5d9d0914d2a6203363af7890f0a642b71a4d10b211e03f9e2fa43800cb6ee`.
  ELF SHA-256: `54eef994058f0de4f0dbcadaf370e3255c7ff6a1b3df3fc6074b16e6c15a9df1`.
- One interim archive operation reported `dns_api.cpp.obj: file truncated`.
  The standalone object validated. A subagent's selective Ninja build also
  triggered dependency work and may have overlapped the parent build. All such
  builds were stopped; subsequent parent-only builds passed. This is a local
  build-coordination failure, not evidence of a device fault.
- Pre-existing dependency warnings: Matter `aligned_storage` deprecation and
  duplicated/out-of-choice `SEC_CERT_DAC_PROVIDER` Kconfig definitions. They
  occur in the clean baseline too. No dependency upgrade or warning suppression
  was used to hide them.
- Docker/CI container build was not executed: Docker Desktop's Linux engine was
  unavailable. Native IDF matches the pinned CI version, and active explicit
  defaults match, but this is not a claim that hosted GitHub CI ran.

The first updated boot reported ready at 4,435 ms; no comparable original boot
measurement was captured. No battery-life or runtime memory improvement was measured. The scan cleanup has a demonstrated error-path ownership fix;
its real-device memory benefit is expected, not benchmarked. Minimum-ever heap
and stack readings decreased during the installed-firmware samples; the stable
largest block and small free-heap changes neither prove a leak nor exclude one.

## Approved deployment and rollback

The user approved the proposed backup, app-only update and reversible tests by
replying "yes". The device was re-identified as ESP32-S3 on COM5, 16 MB flash.
A full 16,777,216-byte backup is stored privately outside this repository, with
its path recorded only in ignored `build/audit-deployment/backup-path.txt`.
Full backup SHA-256: `5a04d28b790491503ebd30a859d20f66a1050237b67f0aebfd489b9fb8dceef3`.
The extracted original application range (0x10000, length 0x700000) validates
as `c65b402*`; rollback SHA-256:
`6c565061d5365a7199dacf7e434b0b1532ab7a4150b80dff9bbfa94b142b83eb`.
Rollback means writing this original app range, not the rebuilt clean-HEAD image.
The original backup is immutable; restoring provisioning would require a separate
recovery decision. Raw logs and flash contents remain private.

The first reviewed image was written at 0x10000 only and esptool verified its
hash. Before reboot, both NVS ranges were read back and were byte-for-byte
identical to the original backup. The application reported its expected full
ELF SHA, Wi-Fi connected, Matter commissioned endpoint 1, and Thread attached.
A child role is a valid attachment; router preference was not changed.

Hardware checks completed on that image:

- Six requested link-drop commands all returned ESP_OK; five actual disconnect
  events were recorded, followed by recovery in approximately four seconds.
- An intentionally invalid replacement Wi-Fi configuration failed and restored
  the previous configuration. A real application reboot retained the original
  SSID and commissioned Matter state. SSIDs were compared privately.
- Reboot status at 33 seconds: Wi-Fi associated 30 seconds, zero disconnects,
  internal free heap 47,239 bytes, largest block 20,480, minimum 12,759;
  LVGL minimum free stack 1,944 bytes. These are samples, not a leak/soak proof.
- REST GET routes returned 200; malformed state, embedded NUL, invalid dataset,
  signed integer, over-limit lifetime and invalid port requests returned 400.
- A 30-second temporary sharing session returned a valid-format code with
  `Cache-Control: no-store`, advertised `_meshcop-e`, expired to stopped and
  withdrew its advertisement. The code was discarded without logging it.
- Normal `_meshcop` was absent from two host discovery captures despite Thread
  attachment. Local pinned IDF source shows publication on child/router/leader
  state changes; Matter can attach before deferred BR initialization. The followup
  reconciles early publication after applying the saved name and refreshes the
  SRV port when the Border Agent becomes active. Final discovery is tested below.
- Camera self-test captured 40 frames with varying luma (sampled min 28, max
  88-110, mean 33-34); no QR decoded in the scene. This proves acquisition, not
  QR interoperability or visible preview quality.
- The user reported the other device functions work and requested a camera
  option in Settings. Added **Settings > Camera test** with live grayscale
  preview, frame/luma/QR-candidate feedback, Repeat and Back. It shares the existing
  worker and PSRAM buffer, serializes ownership with QR scans, and discards
  decoded content. A run ends after 400 poll attempts or Back. Layout checks
  pass for 18 panels plus header. The user subsequently confirmed that the preview changes as the camera moves
  and Back returns to Settings.

Final followup build and app-only flash passed; esptool verified the image hash.
Image: **2,755,280 bytes**, app SHA-256
`8a4924b936c913d2ae7b9fc3d4fd189e17d74395372a1348f48af70cebacd871`.
ELF SHA-256:
`e2a1c75d9ba9bac31378fa24fd45cde1237e1389c3853b3d7f684420a5a64026`.
The running device reports this exact ELF hash, retains the original Wi-Fi and
commissioned Matter endpoint, and REST confirms Thread child attachment.
The reviewed source hashes still match the flashed manifest. The generated
partition table is unchanged; only 0x10000 through 0x2b0fff was erased/written.

All host regressions passed again. Layout: zero problems across 18 panels and
header. On the final image, both normal `_meshcop` and temporary `_meshcop-e`
were discovered; the temporary service expired and withdrew at 30 seconds.
REST valid/malformed checks passed again. One GET state took 3,091 ms and one
rejected POST took 1,484 ms; no low-latency guarantee is claimed. Boot logged one
transient Wi-Fi connect/authentication retry and ND6/RA failures while links were
starting; subsequent connection, attachment and discovery succeeded. No panic
was observed in the captured checks. The user explicitly confirmed the live
camera preview and Back control work.

Ignored evidence: `build/audit-deployment/camera-artifacts.json`,
`final-verification.json`, `camera-host-tests.log`, `camera-build.log`,
`camera-settings-layout.svg`, `rest-validation.json`, `share-validation.json`,
`nvs-preservation.json`, `persistence-verification.json`, and redacted captures.
These tests do not constitute a long-duration soak, fresh commissioning to an
external ecosystem, complete credential exchange, or QR decoding interoperability.

Open limitations/hypotheses: discovery currently selects IPv4 A records, so
IPv6-only/link-local peer discovery still needs an explicit scoped-address
implementation and interoperability test. Full CoAP retransmission/token
correlation, camera driver recovery under repeated faults, callback/UI latency,
headless service fallback and PMIC initialization concurrency deserve targeted
tests; this capture did not demonstrate failures there. Settings are still
multiple NVS keys, not an atomic transaction: error reporting does not promise
all-or-nothing multi-field persistence. No speculative architecture rewrite,
power tuning or cosmetic layout redesign was justified by the available data.

## Protocol references

Pinned source contracts were checked locally. Official references used alongside
them: [ESP-IDF 5.5.4 Wi-Fi API](https://docs.espressif.com/projects/esp-idf/en/v5.5.4/esp32s3/api-reference/network/esp_wifi.html)
for driver storage and scan-result ownership, and
[OpenThread Border Agent API](https://openthread.io/reference/group/api-border-agent)
for ephemeral-key state/callback behavior. Current docs were not used to replace
the project's pinned implementations.
