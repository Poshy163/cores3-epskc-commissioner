# CoreS3 firmware update — 20 November 2026

The bench device now runs ESP-IDF 6.1.1 with ESP-Matter 1.6.1, mDNS 1.15.1 and
quirc 1.2.0~1. Both NVS partitions, the Thread dataset, Wi-Fi provisioning and
the Home Assistant Matter fabric were preserved; nothing needed re-pairing.
Dataset changes no longer reset the Border Agent ID. A second change the same
day replaces the ESP32-H2 radio firmware to stop its periodic resets; see
[H2 radio firmware](#h2-radio-firmware).

## Why ESP-IDF 6.1.1

ESP-Matter 1.6.1 is tested against ESP-IDF 6.0.2: its CI pins v6.0.2 on both
`main` and `release/v1.6.1`, and nothing there exercises 6.1. Both 6.0.3, the
newest release on the tested branch, and 6.1.1 were built and passed the same
device checks; 6.1.1 was kept at the owner's request.

6.0.3 already contains the fixes that motivated the update: memory-safety and
request-smuggling fixes in the HTTP server behind port 8081, OpenThread input
validation (MAC header IEs, Link Accept, Child ID Response, IPv6 fragments) and
Border Agent DTLS session handling, Mbed TLS 4.1.1, and `esp_event` fixes.
6.1.1 adds 62 OpenThread commits, mostly MAC/radio refactoring, for 1.9 KB more
static internal RAM and 32 KB more flash.

The stock H2 RCP reports Spinel RCP API 11 with minimum host API 4, unchanged
across all three host versions, and the 6.1.1 host attached normally.

## Configuration

- `CONFIG_OPENTHREAD_PLATFORM_MSGPOOL_MANAGEMENT=y` is now pinned. ESP-IDF 6.1
  changed its default to n, which would move the 128 OpenThread message
  buffers from PSRAM into internal RAM.
- The local `sdkconfig` was regenerated from `sdkconfig.defaults` and is
  identical to a fresh CI configuration. It picks up the newer SDK defaults:
  an 800 ms interrupt watchdog on PSRAM targets (6.0.3), cross-signed
  certificate-bundle verification (no HTTPS client here uses the bundle), and
  6.1's Wi-Fi-remote weak stubs, which the linker discards.

## Border Agent ID

`thread_join()` wipes OpenThread's persistent settings before applying any
dataset, including the Border Agent ID that commissioners and Home Assistant's
Thread panel use to tell border routers apart. OpenThread kept the old ID in
RAM, so it only changed at the next boot. Every console or touch join, ePSKc
self-fetch and REST dataset write therefore gave the router a new identity.
The wipe also removes the SLAAC secret, SRP server state and the border
router's ULA prefix, which OpenThread regenerates.

`thread_join()` now writes the previous ID back after each wipe. OpenThread's
`otBorderAgentSetId()` neither saves nor refreshes the MeshCoP TXT record when
the value equals the cached ID, so the fix writes a one-bit-different ID first.

During this work, before the fix, the ID went `8aaa0145…` → `55d10403…` →
`6cc132e8…`. On the final build `6cc132e8…` survived an ePSKc self-fetch and a
reboot. Home Assistant's Thread panel shows this router under that ID; the
Matter node is identified by its fabric and is unaffected.

## H2 radio firmware

The H2 reset about three times a day: `Handle radio frame failed: Parse`, then
`RCP failure detected` and a recovery. The ESP32-H2 radio stores the raw PHR
byte, whose top bit is reserved. ESP-IDF's 802.15.4 driver clears that bit for
received data frames but not for acknowledgements, and the RCP's OpenThread
glue uses the byte as the ACK's length. An ACK with the bit set therefore
reached the S3 claiming 128 bytes or more, failed Spinel parsing, and the host
reset the radio as misbehaving. ESP-IDF 6.1.1 and master still clear the bit on
one path only.

`rcp/` builds ESP-IDF 6.1.1's `ot_rcp` example for the H2 plus
`rcp/main/ack_length_fix.c`, which wraps `ieee802154_inner_transmit_done` with
`-Wl,--wrap` and clears the bit before OpenThread reads the ACK. In the linked
image all four driver call sites go through the wrapper. It leaves out the
example's console, external-coexistence and 802.15.4 debug helper components.
Its configuration disables those features, so none of their code was linked,
and without them the build needs nothing from the component registry and its
`dependencies.lock` holds no machine-specific path. The image ships in a
new 640 KB `rcp_fw` SPIFFS partition at `0x720000`, after `matter_nvs`, so no
existing partition moves; the partition table has to be written once. The
merged factory image now ends with `rcp_fw`, so it is about 8 MB and also
erases `matter_nvs`, which clears Matter fabrics on a factory install. At boot
`main/rcp_update.c` flashes the H2 over UART1 with `esp_rcp_update` when the
bundled version is new to it, holding BOOT (GPIO18) and pulsing RESET (GPIO7)
as Espressif's M5Stack border-router example does, then restarts. NVS counts
the attempts, and only a boot that reads the bundled version back from the H2
clears them. After three it stops until `rcp update` is run. The version string
carries the time of `rcp/`'s last commit and fixed-length commit names, so CI
and local builds of the same sources report the same version.

The first flash exposed a deadlock that ordinary boots could also hit. When
Wi-Fi had an address before OpenThread started, which the 12-second flash
guarantees and a fast access point sometimes causes, the border router started
before the camera probe and the device froze: no REST, no console, no replies
on Wi-Fi, Matter unavailable. Backtraces of every task showed a cycle of three
locks. The OpenThread task, inside the firmware's MeshCoP TXT callback, waited
for the mDNS service lock. The mDNS task held that lock while waiting for
lwIP's core lock. lwIP's thread held the core lock while waiting for
OpenThread's task-switching lock to send an MLD report on the Thread
interface. ESP-IDF's own MeshCoP publisher releases the task-switching lock
around its mDNS calls. The firmware's own mDNS calls did not: the TXT refresh,
the MeshCoP port refresh, `_meshcop-e` publish and withdraw, and rename. They
now release it too. The S3 also restarts after every H2 flash, as Espressif's
reference updater does, so the flasher's UART and pin setup never reaches
OpenThread.

Validation on the bench device:

- With the restart disabled, the boot after a flash froze in 2 of 2 runs before
  the lock fix and completed in 2 of 2 after it: TXT refresh, camera probe,
  REST and "commissioner ready" by 17.4 s, with MLE traffic still processed a
  minute later.
- With the restart, `rcp update` flashed the H2 in 11.7 s, restarted, read the
  bundled version back and cleared the attempt count; the device was ready in
  5.4 s. Two later boots started the border router before the camera probe and
  completed normally.
- `rcp` shows the running, bundled and flashed versions equal. The active
  dataset digest and Border Agent ID `6cc132e8…` were unchanged after an ePSKc
  self-fetch and a reboot, `camtest` passed, and Home Assistant kept the node
  available with battery reports. No RCP failure, parse error, panic, watchdog
  or assert lines were logged.
- `nvs` and `matter_nvs` were byte-identical across every flash.
- The published image is built from `b544c18`, and `firmware/build-info.json`
  records it. The commit gave the radio firmware a new version, so the image's
  first boot flashed the H2 in 11.7 s and restarted, and the next boot verified
  it. Two ePSKc self-fetches, taking 10.7 s and 9.6 s, and a reboot left the
  dataset and Border Agent ID unchanged. `camtest` passed, and Home Assistant
  reports `b544c18` with battery reports after the reboot.
- Internal heap after boot was 50.2 to 50.7 KB free on every boot. The
  largest free block ranged from 19.5 to 31.7 KB across boots of the same
  code, and the self-fetch passed on the boot with the smallest.

The resets came about three times a day, so a short session cannot show that
they stopped; the logs over the following days will.

## Notes

- One build stopped with a GCC internal compiler error (segfault in register
  allocation) while the PC's commit charge was near its limit. The file built
  cleanly on retry. Build with `ninja -j 10` or fewer when the PC is busy;
  ESP-Matter's own CI caps jobs at 6.
- `ui.c` produces 75 `-Wdeprecated-declarations` warnings for LVGL 9.6's
  `lv_obj_add_flag`/`lv_obj_remove_flag`/`lv_obj_has_flag`. They predate this
  update and do not affect behaviour.
- `/logs?boot=previous` reports the current boot's `reset_reason`, not the
  previous boot's.
- In the self-fetch the OpenThread task spends about 7 s on EC-JPAKE. On 6.0.3
  one inbound UDP datagram missed the 10-entry task queue's 100 ms wait and was
  dropped; DTLS retransmitted it. With the radio update, runs logged between 0
  and 29 such drops and finished in 9.5 to 10.9 s. Earlier runs that day logged
  them too, before the lock change.

## Rollback

The October image and its ELF are in `build/rollback-ccf163d-idf602/`; the
6.0.3 build is in `build/idf6-v6.0.3/`. Writing either app image at `0x10000`
leaves both NVS partitions untouched.
